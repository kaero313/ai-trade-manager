## 1. 판정

BotConfig heartbeat lost update와 외부 SystemConfig 무검증 문제를 코드 수준에서 해소했습니다.
runtime 상태는 전용 컬럼으로 분리됐고, 연구 프로필과 모든 외부 SystemConfig 변경은 version을 기준으로
stale writer를 차단합니다. REST, AI Banker, Telegram은 같은 중앙 registry·검증·원자 저장 서비스를
사용하며 Settings는 실제 production 소비 키를 표시합니다.

Docker의 격리 PostgreSQL 16에서 `d5e8a1c4b7f2` backfill·check constraint·downgrade/re-upgrade와
다중 세션 경합을 모두 확인했습니다. 누락돼 있던 BotConfig heartbeat와 설정 CAS의 실제 독립 세션
경합 테스트도 추가했으며, PostgreSQL marker를 migration 왕복 전후 두 번 통과했습니다. 따라서
**구현·로컬 PostgreSQL 16 최종 검증 완료 / 원격 CI 미실행**으로 판정합니다.

### 독립 Reviewer 확인

최초 검토에서는 Settings가 저장 시점의 최신 query version을 붙여 편집 중 바뀐 설정 위에 stale draft를
재기반할 수 있다는 P1 동시성 결함이 발견됐습니다. 키별 최초 편집 version snapshot을 추가하고, 기준
version과 현재 query version이 다르면 API를 호출하지 않은 채 draft를 폐기·재조회하도록 수정했습니다.
`version 3` 편집 중 query가 `version 4`로 갱신되는 회귀 테스트에서 mutation 0회와 refetch를 확인했습니다.

수정 후 독립 재검토는 승인됐습니다. 중앙 SystemConfig 경계 우회, legacy writer fallback, provider 전용
reset 계약 훼손, P0 거래 모드·Kill Switch·중앙 주문 경계 회귀는 발견되지 않았습니다. 실제 PostgreSQL
16 migration·backfill·다중 세션 CAS까지 후속 검증에서 완료했습니다.

## 5. 운영 확인 사항

- migration을 코드보다 먼저 적용해야 합니다. 구 schema에서 runtime writer나 version API를 실행하지
  않습니다.
- `409`를 받은 클라이언트는 최신 version을 다시 읽고 운영자가 변경 내용을 재검토해야 합니다.
- `503`과 `detail.saved=true`는 DB 저장은 성공하고 scheduler reload만 실패했다는 뜻입니다. 같은
  payload를 무조건 재전송하지 않습니다.
- provider 상태는 일반 `/system/configs` mutation에 포함하지 않고 전용 reset endpoint를 사용합니다.
- 거래 모드, 주문 Gate와 `live_order_v2_enabled`는 계속 P0 전용 절차를 사용합니다.
